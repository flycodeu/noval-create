# P2 - 批量工作流运行注册表潜在残留

> 优先级：P2（中等）
> 影响范围：长时间运行内存
> 实现难度：低
> 类别：后端-批量工作流

---

## 问题

`batch-workflow.service.ts` 使用 `activeBatchWorkflows` 记录当前正在执行的批量工作流，用来防止重复启动。

原始实现虽然已经在各条主执行链路的 `finally` 中做了 `delete()`，正常异常抛出并不会跳过 `finally`，所以文档里“异常可能绕过 finally 导致直接泄漏”的判断并不准确。真正更合理的风险是：

- 如果后续维护中有人改坏退出路径，注册表会完全依赖 `finally` 清理
- 如果任务状态已经不再运行，但进程内注册表残留，后续恢复/重启同任务时可能被误判为“仍在运行”

## 原因

- `activeBatchWorkflows` 实际上是 `Set<number>`，不是 `Map`
- 旧实现只有“进入时 add / 退出时 delete”这一层保障
- 启动、恢复、查询状态前没有做一次“失活任务清扫”

## 解决方式

1. 保留现有 `try-finally` 清理
2. 新增注册表自愈清扫：
   - 每次注册运行中的 workflow 前，先把非运行态 / 不存在 / 类型不匹配的条目清掉
   - 每次读取批量 workflow 状态时也先做一次清扫
   - 恢复任务前如果注册表仍标记该任务为运行中，直接阻止重复恢复
3. 文档同步纠正“Map 泄漏”与“finally 会被普通异常跳过”的错误描述

## 是否解决

已解决 — 2026-04-06

当前状态：

- 正常异常路径继续由 `finally` 保证删除
- 额外增加了失活条目自愈清理，避免运行注册表长期残留
- 恢复任务前会阻止重复恢复，避免脏注册表造成双开或误判

## 预期效果

- `activeBatchWorkflows` 不会因为失活条目长期残留而持续增长
- 长时间运行的应用内存保持稳定
- 批量任务恢复逻辑更稳，不会被旧注册表状态误伤
