# P1 - 上下文压缩仍是自由文本拼接而非最小实体卡

> 优先级：P1（严重）
> 影响范围：上下文稳定性、批次间关联、长任务 token 预算
> 实现难度：中高

---

## 涉及模块

- `electron/services/context.service.ts`
- `electron/services/story-memory.service.ts`
- 关联影响：章节生成、人物/物品/线程/时间轴等所有需要上下文的生成链路

## 问题

当前系统已经有角色状态、关系摘要、长文记忆、时间轴摘要、活跃线程等上下文模块，但主要表达形式仍然是较长的自然语言文本块，而不是适合长篇拆批生成的“最小实体卡”。

对于百万字系统，这会带来两个直接问题：

- 上下文越积越长，批量任务和长任务更容易挤占 token 预算
- 不同批次、不同模块拿到的上下文形态不稳定，很难保证同一角色、同一势力、同一物品在多轮生成中总是携带同一组核心约束

用户提出的“主角：姓名、年龄、关系；NPC1：同样结构”的需求，本质上就是要把上下文从“散文式摘要”升级成“结构化最小卡片”。

## 原因

`electron/services/context.service.ts` 中：

- `getImportantCharacters()` 目前最多选取 15 个角色
- `buildCharacterStates()` 会把实体类型、种族、职业、身份、性格、目标、内在冲突、关系张力、说话方式等内容拼成一整行字符串

`electron/services/story-memory.service.ts` 中：

- `buildStoryMemoryPromptSummary()` 会把摘要、人物状态、人物关系、物品账本、时间轴、活跃线程等拼成多段长文本

这说明系统已经有“记忆”和“摘要”，但还没有把这些信息压成稳定的最小字段集。

## 为什么前三轮修复后仍然可能发生

前三轮已经把角色上下文数量从 8 提升到 15，也引入了分层记忆、检查点、活跃线程提醒。  

但这些修复主要提升的是“能看见更多内容”，不是“是否用正确的结构看见内容”。如果表达层仍然是大段自由文本，那么批量拆分、续跑、跨模块复用时仍然会出现上下文臃肿和约束漂移。

## 解决方式

1. 把上下文明确拆成 3 层：
   - 固定世界底座
   - 最小实体卡
   - 动态召回记忆
2. 角色卡改成稳定字段集，例如：
   - 姓名
   - 年龄/外观阶段
   - 身份/阵营
   - 与主角关系
   - 当前状态
   - 当前目标
   - 说话特征
   - 禁忌/硬约束
3. 物品、地点、势力、线程也使用同类最小卡，而不是继续直接塞自然语言段落
4. 为每类卡片设置字段上限和长度上限，避免重新膨胀成大段 prose
5. 批量生成的下一批只携带卡片与摘要，不再反复拼接冗长的全量文本

## 是否解决

未解决 — 2026-04-05（第五轮新增）

当前状态：半闭环

- 系统已经有摘要、记忆、关系与状态信息
- 但上下文主形态仍偏自然语言拼接，而不是严格结构化的最小实体卡

## 预期效果

- 拆批生成时，上下文能稳定保留核心信息，而不是每批都带一段不同写法的长摘要
- 百万字项目里 50+ 角色、多个势力和大量物品仍能以可控成本进入 prompt
- AI 更容易抓住“必须遵守的核心约束”，而不是被长文本稀释注意力
