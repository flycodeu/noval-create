# 审校反哺与复现率闭环

## 一、目标

让 Critic 和章节门不只是“事后指出问题”，而是能把反复出现的问题自动写回下一章生成约束。百万字生成最怕同一问题跨章复现，必须建立问题类型、复现率、硬约束、复检之间的闭环。

## 二、当前已完成

- `buildChapterReviewPrompt` 已要求审校输出连续性、故事弧、上下文漂移、真实度、追读、语言、代价、反转、章节功能等 JSON。
- `chapterGateRuns` 会持久化章节门结果。
- `quality-dashboard.service.ts` 已能聚合趋势、热力图和风险告警。
- `chapter.service.ts` 会根据部分检测结果触发修复。
- 已新增 `feedback-recurrence.service.ts`，将 `reviewNotesJson`、`chapterGateRuns`、合同校验结果和 anti-AI 命中归一化为统一复现问题。
- 已把 `workspace-quality.service.ts` 里的解释腔、模板衔接、空转修辞、锚点不足、立场发虚等“人类化信号”写回 `reviewNotesJson`，并进入同一条复现链路。
- `context.service.ts` 已把近章复现问题注入 `hardConstraintContext`，作为下一章不可裁剪硬约束。
- `chapter.service.ts` 已在章节门落库后同步通用复现任务状态。
- `batch-workflow.service.ts` 已能在结构/连续性类问题 5 章窗口高风险复现时自动暂停章节批次。
- `quality-dashboard.service.ts` 与质量看板已展示通用复现问题、升级状态、卷级聚合和章节明细。

## 三、当前闭环结果

- `reviewNotesJson`、`chapterGateRuns`、合同兑现验证和 anti-AI 命中已统一归一化为复现问题类型。
- `workspace-quality` 的人类化诊断不再只停留在工作区体检，而是会回流到章节审校、下一章硬约束和质量仪表盘。
- 连续 2 章同类问题会自动升级为下一章 `【近章必须避免】` 硬约束。
- 5 章内出现 3 次的高风险问题会生成系统修订任务；结构/连续性类问题会进一步触发批次暂停。
- 对解释腔、模板衔接、空转修辞、锚点不足、立场发虚等人味问题，现已支持“高严重度 + 5 章窗口复现”后进入暂停建议。
- 质量仪表盘可追溯每类问题的来源章节、升级状态、卷级分布和章节命中详情。

## 四、详细设计

### 4.1 FeedbackRecurrenceService

当前实现采用 `feedback-recurrence.service.ts`，而不是单独新增 `feedback-compiler.service.ts`。

输入：

- 最近 3-5 章 `reviewNotesJson`。
- 最近 3-5 章 `chapterGateRuns`。
- 语言漂移指标。
- 合同验证结果。
- 反 AI 规则命中。

输出：

```ts
FeedbackRecurrenceDashboardSummary {
  overview: {
    hitChapterCount: number
    recurringIssueCount: number
    promotedIssueCount: number
    highRiskIssueCount: number
    pauseSuggestedIssueCount: number
  }
  promotedIssues: FeedbackRecurrencePromotedIssueSummary[]
  recentAlerts: FeedbackRecurrenceAlert[]
  chapterSignals: FeedbackRecurrenceChapterSignal[]
}
```

### 4.2 初始问题类型

第一阶段支持以下问题：

- `cost_evaporation`：代价蒸发。
- `forced_reversal`：强行反转。
- `too_smooth`：主角顺推。
- `ai_slogan`：口号句。
- `template_emotion`：模板情绪。
- `pov_drift`：视角漂移。
- `thread_stalled`：支线空转。
- `dialogue_homogenized`：对白同声化。

### 4.3 升级规则

| 条件 | 动作 |
|---|---|
| 单章高严重度 | 写入本章重写建议 |
| 连续 2 章同类问题 | 下一章硬约束 |
| 5 章内出现 3 次 | 批次暂停，生成修订任务 |
| 全卷持续出现 | 质量仪表盘标红 |

### 4.4 Prompt 注入方式

在下一章上下文中增加：

```md
【近章必须避免】
- 近 2 章连续出现代价蒸发：本章任何损失、伤势、资源消耗都不得一段内恢复。
- 近 3 章对白同声化：本章主要角色必须体现不同称呼、句长和停顿。
```

这部分应进入硬约束预算，不能作为可裁剪软上下文。

## 五、数据结构策略

当前版本未新增独立快照表，直接复用：

- `chapters.reviewNotesJson`
- `chapter_gate_runs.topIssueKeysJson`
- `anti_ai_rule_hits`
- `revision_tasks`

在 `buildChapterContext` 中动态生成下一章硬约束；如后续需要历史审计，再补独立快照表。

## 六、实施步骤

1. 定义问题类型映射，将 reviewNotes 和 chapterGate 项归一化。
2. 新增 `feedback-recurrence.service.ts`，统计最近 3-5 章复现问题。
3. 将输出接入 `context.service.ts`，作为硬约束候选。
4. 在质量仪表盘展示复现率、升级状态和章节命中详情。
5. 批次总控读取高风险复现，决定是否暂停下一批。

## 七、验收标准

- 下一章 prompt 能看到“近章必须避免”。
- 同类问题连续 2 章出现后会自动进入硬约束。
- 5 章内 3 次复现会生成任务或暂停批次。
- 用户能追溯某个复现问题来自哪些章节。
- 已通过 `npm run typecheck` 与 `npm run test:unit` 验证。

## 八、风险与建议

- 不要把所有审校意见都升级为硬约束，否则 prompt 会变得噪声很大。
- 升级规则要按问题类型区分，语言问题和结构问题阈值不同。
- 反馈约束要短、具体、可执行，避免变成新的提示词腔。
