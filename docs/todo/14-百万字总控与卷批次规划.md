# 百万字总控与卷批次规划

## 一、目标

把当前“单章生成能力”提升为“百万字生产调度能力”。系统要能围绕 80-120 万字项目，按卷、批次、章节组织生成和验收，而不是让用户手动连续点击 300 次。

推荐默认规模：

- 总字数：80-120 万字。
- 章节数：250-400 章。
- 每章：2500-4000 字。
- 每卷：25-35 章。
- 每批：8-15 章。
- 每 10 章形成一个长期记忆 checkpoint。

## 二、当前已完成

- [x] 总规模目标已由 `novels.targetWords`、卷/部/章结构和章节目标字数共同承载，不再依赖口头约定。
- [x] 结构侧已支持按故事弧连续补齐下一批章节细纲，并返回 `batchStart / batchEnd / completed / message`，可明确显示当前批次范围和是否可继续下一批。
- [x] `tasks` 工作流已承载批次级运行信息，包括 `requestedCount / batchSize / totalBatches / resumeCursor / generatedCount / message`。
- [x] `batch-workflow.service.ts` 已支持批量流程暂停、恢复、异常保进度、应用重启后继续执行。
- [x] 任务中心已支持查看批次任务详情、继续后台流程、重试失败任务和恢复入口提示。
- [x] `story_memory_checkpoints` 已支持小说级、卷级、部级 checkpoint，并支持 stale 检测、刷新和锁定。
- [x] 创作引导页、正文写作页和任务中心已形成“可继续推进 / 先修关键冲突 / 需要处理问题”的继续提示与恢复前风险提醒。

## 三、已补齐的问题

- [x] 不再缺少“百万字生产计划”承载位。当前实现采用轻量方案：总字数走 `novels.targetWords`，卷批次边界走结构数据，批次运行态走 `tasks`。
- [x] 已有批次级状态和进度，不再只能看到单章状态。
- [x] 进入下一批前已经能给出继续提示，不再完全依赖用户自行判断。
- [x] 已有批次失败恢复策略，暂停后继续不会重做已完成批次。

## 四、当前实现口径

### 4.1 计划承载方式

当前版本没有单独新增 `MillionNovelPlan` 表，而是把百万字总控拆到已有模型中：

```ts
MillionNovelRuntime {
  targetWords: novels.targetWords
  structurePlan: volumes / parts / chapters
  batchProgress: tasks.progressJson
  batchInput: tasks.inputJson
  recoveryHint: tasks.recoveryHintJson
  checkpoints: story_memory_checkpoints
}
```

这样做的好处是：

- 不引入额外孤立表。
- 批次推进和任务中心天然打通。
- 恢复入口、报错、重试、暂停状态都能复用现有任务基础设施。

### 4.2 批次状态的实际落点

实现上把“任务状态”和“业务批次信息”拆开承载：

| 层级 | 当前位置 |
|---|---|
| 任务生命周期 | `pending / running / paused / success / failed / cancel_requested` |
| 批次进度 | `requestedCount / batchSize / totalBatches / resumeCursor / generatedCount` |
| 批次说明 | `message / errorMessage / currentChildTaskId / recoveryHintJson` |

这比单独再造一套 `plan -> draft -> gate -> canon -> checkpoint -> completed` 状态机更稳，因为暂停、恢复、异常回退和任务中心展示已经是统一能力。

### 4.3 继续/修复总灯

当前实现不是单独新增一个“百万字总控总灯页”，而是把继续判断分散到最贴近操作的页面上：

- 创作引导页按分数给出 `结构稳定 / 可继续推进 / 先修关键冲突`。
- 正文写作页按健康分给出 `结构稳定 / 可继续推进 / 需要处理问题`。
- 任务中心在恢复暂停流程前，会额外提示 `stale checkpoint` 和 `stale asset` 风险。
- 批量补齐章节细纲后，会明确返回“当前故事弧已补齐”或“可继续生成下一批”。

因此，当前“质量总灯”的落地方式是“继续提示 + 恢复前阻塞提醒”，而不是单个独立组件。

### 4.4 恢复策略

- 批量流程异常时会保留当前进度，并把任务置为 `paused`。
- 应用重启后，后台批量流程也会被重整为可恢复状态，不会直接丢进度。
- 继续任务时会从 `resumeCursor + 1` 对应的批次恢复。
- 已完成批次不会被自动重跑覆盖。
- 恢复前若检测到长期记忆或相关资产已过期，任务中心会先给出风险提醒。

## 五、数据结构与表

当前版本已经足够支撑百万字批次总控，不需要立刻新增 `novel_generation_batches`：

- `tasks`：承载批次输入、运行态、恢复入口、报错和暂停/继续。
- `chapters`：承载章节范围、目标字数、批次补齐后的实际内容。
- `story_memory_checkpoints`：承载小说级、卷级、部级长期记忆摘要与刷新状态。

后续如果要做“跨卷批次审计、批次快照回滚、批次 SLA 报表”，再单独补 `novel_generation_batches` 会更合适；当前阶段不是必须项。

## 六、验收标准

- [x] 用户能看到当前批次覆盖的章节范围。
- [x] 批次可以暂停、恢复、失败后继续。
- [x] 已完成批次不会因为恢复动作被重复覆盖。
- [x] 进入下一批前系统能给出“可继续 / 需处理问题”提示。
- [x] 检查点和上下文过期状态可被感知，不再黑盒推进。

## 七、风险与后续优化

- 当前总控已经可用，但“正文章节批次 orchestrator”仍以现有任务和页面能力组合承载，后续可以再抽成更显式的专用编排器。
- 质量总灯当前分布在引导页、写作页和任务中心，后续可以收敛成统一的批次总览卡。
- 如果后面要支持真正的跨卷回滚和批次审计，再补独立批次表会更自然。
