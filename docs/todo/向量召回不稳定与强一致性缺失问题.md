# 向量召回不稳定与强一致性缺失问题

关联总文档：[百万字小说生成问题分析与扩展方案](./百万字小说生成问题分析.md)

## 1. 问题定义

当前系统已使用向量召回补足历史记忆，但向量召回的本质是“相似补充”，不是“状态保证”。百万字场景下，如果把一致性寄托给召回，相当于把关键事实交给概率机制。

## 2. 当前代码现状

- `electron/services/context.service.ts` 使用 `findSimilarFragments` 召回相关历史片段。
- 同文件会把召回结果整理成 `recalledMemory` 注入 prompt。
- 向量召回的失败被视为非阻塞，不影响主流程。
- `electron/services/embedding.service.ts` 负责 embedding 存储和相似度检索。

## 3. 目前已解决 / 部分解决 / 未解决

- 已解决：系统已经引入历史片段检索，能补足部分远距离记忆。
- 部分解决：召回对“提到过的人/物/事件”有帮助。
- 未解决：关键事实的命中和稳定性没有保障。

当前判断：`部分解决`

## 4. 潜在风险

- 相似文本被召回，但真正关键的那一条没有被召回。
- 同一问题在不同章节命中不同历史片段，造成口径波动。
- 召回内容存在语义相近但状态已过期的情况。

## 5. 原因分析

- 向量召回偏语义相似，不偏状态有效性。
- 历史片段适合补充背景，不适合承担当前状态约束。
- 当前召回缺少“过期判断”和“状态优先级判断”。

## 6. 扩展方案

- 保留向量召回，但明确降级为背景补充层。
- 关键状态、关键伏笔、关键人物关系改为结构化读取。
- 对召回内容增加“时间有效性”和“状态版本”判断。
- 召回只负责找补充说明，不负责定义当前事实。

## 7. 建议的数据结构 / 指标 / 页面能力

- `recalledMemorySource`：记录召回片段来源章节和类型。
- `stateVersion`：关键状态的当前版本号。
- `staleRecallCount`：召回到过期信息的次数。
- 诊断页新增“召回依赖率”“过期召回率”。

## 8. 实施优先级

等级：`A级`

等级说明：重要，但更适合与状态账本和硬约束层一起收敛。

原因：不是最先做的模块，但必须在长期状态账本落地前后一起收敛。

## 9. 验收标准

- 向量召回不再承担关键状态定义职责。
- 关键人物、物品、伏笔状态优先来自结构化账本。
- 召回内容可追踪来源和过期状态。
- 长距离回查中，因召回偏差导致的事实冲突明显下降。
