# 37 - 生成步骤与流水线问题分析

## 一、当前生成流水线架构

```
用户输入(背景/设定) 
  → 13 步引导流程(立项到写前准备)
    → 章节合同(结构承诺)
      → 正文五阶段流水线
        → 章后回写(状态同步)
          → 修订中心(质量闭环)
```

### 1.1 五阶段生成流水线

```
Scene Plan → Draft → Review → Rewrite → Finalize
  (场景规划)  (初稿)   (审校)   (重写)    (定稿)
```

**每阶段的 AI 引擎配置**（ai-engine.service.ts）：

| 阶段 | Token 预算系数 | 温度上限 | 上下文模式 |
|------|---------------|----------|------------|
| chapter_planning | 0.62 | 0.85 | balanced |
| chapter_generation | 1.0 | 0.85 | 由执行模式决定 |
| chapter_review | 0.72 | 0.35 | balanced |
| chapter_rewrite | 1.08 | 0.55 | 由执行模式决定 |

### 1.2 执行模式（五档）

| 模式 | 温度偏移 | Token 比例 | 上下文策略 | 审校深度 |
|------|---------|------------|------------|----------|
| fast | -0.05 | 72% | trimmed | lite |
| balanced | 0 | 100% | balanced | standard |
| premium | -0.03 | 118% | max_coverage | deep |
| review_first | -0.12 | 105% | max_coverage | deep |
| cost_saver | -0.08 | 58% | trimmed | lite |

## 二、流水线存在的问题

### 2.1 Scene Plan 阶段的局限

**问题**：场景规划目前只做单章内的场景分解，没有考虑**章间连接**。

**具体表现**：
- 上一章结尾角色在 A 地点，新章第一个 scene 可能突然出现在 B 地点，缺乏位移交代
- 上一章情绪高昂，新章开场可能直接跳到平叙，缺乏情绪衔接
- 时间跨度不明确——两章之间过了多久？

**建议**：在 Scene Plan 之前增加 **Chapter Bridge** 微步骤：
- 读取上一章最后 300 字 + 当前章目标
- 生成"衔接指令"：地点过渡方式、时间跳跃幅度、情绪过渡策略
- 将衔接指令注入第一个 scene 的约束

### 2.2 Review 阶段的覆盖面不均

**当前审校维度**（ReviewNotes 接口定义）：
- `critical_fixes`：关键修复
- `continuity_risks`：连续性风险
- `arc_progress_risks`：弧线进展风险
- `context_drift_risks`：上下文漂移风险
- `realism_risks`：真实性风险
- `coherence_risks`：连贯性风险
- `reader_hook_risks`：读者钩子风险
- `language_risks`：语言风险
- `human_language_repairs`：人类语言修复
- `genre_hollowing_risks`：题材空洞化风险

**问题**：审校维度全面，但**权重不明确**。系统同等对待所有维度，导致 Rewrite 阶段可能同时修复 10 个小问题却忽略 1 个大问题。

**建议**：
1. 为每个审校维度增加**严重性评分**（1-5 分）
2. Rewrite 阶段只处理评分 ≥3 的问题，其余留给下次迭代
3. 如果 critical_fixes 评分为 5，直接触发**完整重写**而非局部修复

### 2.3 Rewrite 阶段的保守倾向

**问题**：Rewrite 的温度上限是 0.55（低于 Draft 的 0.85），这意味着重写倾向于**保守修改**。当 Draft 质量差时，保守的 Rewrite 可能只是"微调"而非真正改善。

**建议**：
1. 当 Review 报告 critical_fixes 数量 ≥3 时，提高 Rewrite 温度到 0.70
2. 当 continuity_risks 严重时，改用 max_coverage 上下文模式确保重写能看到足够上下文
3. 增加**重写质量对比**：Rewrite 后再做一次 mini-review，如果评分没有显著提升则标记需要人工介入

### 2.4 Finalize 阶段的功能缺失

**当前状态**：Finalize 主要做合同验收和状态锁定。

**缺少的收尾工作**：
1. **章节指纹生成**：提取本章的关键表达、新角色状态、新伏笔，作为后续章节的"章节记忆卡"
2. **全局一致性快检**：检查本章是否引入了与已有设定矛盾的新信息
3. **下一章预备**：基于本章结尾自动生成下一章的"开场建议"

### 2.5 章后回写的时序风险

**问题**：章后回写（Writeback）更新角色状态、伏笔账本、时间轴等。但如果用户**批量生成多章**，回写顺序是否严格按章节顺序执行？

**风险场景**：
- 第 10 章回写更新角色 A 受伤
- 第 11 章在第 10 章回写完成前开始生成
- 第 11 章的上下文中角色 A 还是健康状态
- 结果：第 11 章角色 A 表现得好像没受伤

**建议**：
1. 批量生成模式下强制**串行回写 + 串行生成**
2. 或者在每章生成前做**回写完成检查**，未完成则等待
3. 在 PipelineBar 中显示回写状态，让用户知道系统在等待

## 三、Prompt 执行层问题

### 3.1 Prompt Override 的风险

**问题**：`applyPromptOverride()` 允许修改基线提示词。如果覆盖逻辑不当，可能**削弱 AI 味约束**。

**建议**：
1. Override 时保护 GLOBAL_WRITING_RULES 的核心约束不被覆盖
2. 增加 override 审计日志——记录每次覆盖的内容和来源
3. 在质量仪表盘显示"本章使用了 N 个 prompt override"

### 3.2 Variation Hint 的确定性问题

**当前机制**：重试时使用 `(attemptNumber - 2) % hints.length` 选择变体提示。

**问题**：
- 变体提示是**确定性选择**（相同 attempt 编号总是相同提示）
- 如果核心上下文过于约束，不同 hint 可能产生相似输出
- 没有检查变体输出是否真正与前次不同

**建议**：
1. 在选择 hint 后，追加前次失败输出的前 200 字作为"避免"指令
2. 对变体输出做简单相似度检查（字符级 Jaccard），相似度 > 0.7 时自动切换下一个 hint

### 3.3 Token 估算的安全裕度

**当前设定**：10% 安全裕度。

**实际风险**：
- 中文文本的 token 化因模型不同差异显著（GPT-4 vs Claude vs 国产模型）
- 10% 裕度在使用 GPT-4 时可能足够，但用某些国产模型时可能不足
- token 超出导致上下文被截断，直接影响生成质量

**建议**：
1. 按模型家族配置不同的安全裕度（OpenAI 10%、Claude 12%、国产 15%）
2. 在 context.service 中增加**截断告警**——当实际 token 超出估算时记录到质量日志

## 四、优化优先级

| 优先级 | 问题 | 影响范围 | 实施难度 |
|--------|------|----------|----------|
| P0 | 章间衔接策略 | 每一章 | 中 |
| P0 | 批量生成回写时序 | 批量模式 | 低 |
| P1 | Review 维度权重 | 审校质量 | 低 |
| P1 | Rewrite 温度自适应 | 重写效果 | 低 |
| P1 | Token 安全裕度适配 | 全链路 | 低 |
| P2 | Finalize 章节指纹 | 长篇一致性 | 中 |
| P2 | Prompt Override 保护 | 系统安全性 | 低 |
| P2 | Variation 输出去重 | 重试效果 | 中 |
