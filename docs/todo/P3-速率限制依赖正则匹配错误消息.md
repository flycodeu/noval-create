# P3 - 速率限制重试依赖正则匹配错误消息

> 优先级：P3（改进）
> 影响范围：重试机制鲁棒性
> 实现难度：中
> 类别：后端-任务系统

---

## 问题

原有速率限制检测主要通过正则匹配 error message 字符串来判断是否为限流错误。当 API 提供商更改错误消息格式时，检测会失效，导致本应重试的请求直接失败。

## 原因

- `electron/services/task.service.ts` 的 `isRateLimitError()` 与 `getRateLimitDelayMs()` 主要消费错误文本
- 各适配器在 HTTP 非 2xx 时只抛普通 `Error`，没有把 `statusCode` / `Retry-After` 结构化传上来
- 不同 API 提供商的限流错误格式各异，正则难以全覆盖

## 解决方式

1. 适配器在 HTTP 非成功响应时，保留结构化错误元数据：
   - `statusCode`
   - `retryAfterMs`（从 `Retry-After` 头解析）
2. `task.service.ts` 优先使用结构化字段：
   - `429` 直接视为限流
   - `retryAfterMs` 直接决定退避等待时间
3. 原有正则匹配保留为降级兜底，用于 provider 业务错误体或未结构化错误

## 是否解决

已解决 — 2026-04-06

当前状态：

- OpenAI / Anthropic / Aliyun / Baidu 的 HTTP 错误都会带上结构化限流元数据
- DeepSeek / Custom 继承 OpenAI 适配器，因此自动获得同样行为
- 任务层现在优先看 `statusCode` 与 `retryAfterMs`，不再只靠脆弱的错误文本匹配

## 预期效果

- 限流检测更加可靠，不依赖脆弱的字符串匹配
- 能正确读取 `Retry-After` 头来决定重试等待时间
