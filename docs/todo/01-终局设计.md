# 终局设计

## 一、目标

在长篇早期锁定最终收束方式，避免“中段很强、后段失控”。终局设计负责回答：这本书最后如何收、兑现什么、保留什么、最后一幕是什么。

## 二、当前已完成

- [x] `src/shared/story-settings.ts` 已有 `ending` 与 `endingType` 字段。
- [x] `src/pages/Novel/CoreSettings/index.tsx` 的故事设计页已经允许编辑结局方向。
- [x] 已新增独立页面 `src/pages/Novel/Endgame/index.tsx`，并接入 `/novels/:id/endgame`。
- [x] `novels.settings_json` 已新增 `endgame_design` 块，包含 `endingMode / finalConflict / themeAnswer / mustDeliverPromises / payoffChecklist / deliberateUnknowns / finalImage / lastScene`。
- [x] 工作台导航、推荐流程、Guide / Studio / Overview 已接入 `终局设计` 的就绪度与入口。
- [x] `electron/services/context.service.ts` 的 `StoryProfile` 已新增 `endgameDesignSummary`，并进入故事核心上下文。
- [x] `electron/services/timeline.service.ts` 和部分故事核心摘要服务已能读取终局摘要，不再只依赖一句 `ending`。
- [x] `终局设计` 已可把“必须兑现的承诺 / 长线回收清单”同步成独立的 `endgame_commitments / foreshadow_ledger` 资产。
- [x] `卷级设计中心`、`章节合同 / 场景合同` 已能直接引用终局承诺。
- [x] 质量监控已新增 `endgame_debt` 专门债务指标。

## 三、当前未完成

- 无。当前主链路已经落地，后续主要继续细化卷后审计与写后对账，不影响完成判定。

## 四、模块价值

- 长篇的后期失控，往往不是因为前面没内容，而是因为没有提前锁定“最后要落到哪里”。
- 当前 `ending` 更像一句结局说明，不足以约束数百章的兑现链。

## 五、当前能力结构

- 已有独立页面：`终局设计`
- 页面核心字段：
  - `结局类型`
  - `最终冲突对象`
  - `主题答案`
  - `必须兑现的承诺`
  - `长线伏笔回收清单`
  - `故意保留的未解释项`
  - `终章意象`
  - `最后一幕`
- 页面输出已经进入：
  - 卷级设计的收束基准
  - 伏笔账本的最高优先级回收依据
  - 章节合同的终局对齐约束

## 六、页面与交互

- 放在 `世界规则` 与 `故事设计` 之间，作为长篇中枢约束页。
- 页面顶部显示“当前终局清晰度”与“未绑定的终局承诺数量”。
- 提供从 `故事设计` 自动带入 `ending / endingType` 的初始化按钮。
- 允许把“必须兑现的承诺”一键同步到伏笔账本草稿。

## 七、数据结构 / 状态字段

- 当前继续挂在 `novels.settings_json` 中，使用 `endgame_design` 块。
- 核心字段：
  - `endingMode`
  - `finalConflict`
  - `themeAnswer`
  - `mustDeliverPromises`
  - `payoffChecklist`
  - `deliberateUnknowns`
  - `finalImage`
  - `lastScene`

## 八、与现有模块的关系

- `故事设计` 负责主线推进与结局方向。
- `终局设计` 负责最终收束细节与兑现边界。
- `伏笔与回收账本` 负责把终局要求拆成具体回收任务。
- `卷级设计中心` 负责把终局压力分摊到各卷。

## 九、验收标准

- 可以独立维护终局信息，而不是只在故事设计里留一句结局描述。
- 至少支持 1 个终局类型、1 个最终冲突、1 个主题答案、1 组兑现承诺。
- 终局承诺能被卷级设计、伏笔账本、章节合同引用。
- 质量监控可以识别“终局承诺长期未被服务”的风险。
