# 支线伏笔回收推进器

## 一、目标

让百万字长篇里的支线和伏笔不悬空、不乱推进、不靠一句“提到名字”糊弄。系统要明确本章哪些线必须推进，哪些只是背景，哪些需要延期说明。

## 二、修复状态

- 已完成 支线/伏笔语义化判定：合同校验已明确区分 `mentioned / advanced / blocked / paid_off / stale`，不再把“提到名字”直接算推进。
- 已完成 伏笔回收条件动作化：`foreshadow_ledger`、服务层、写回链路、前端表单已接入 `payoffSceneAction / requiredEvidence / readerVisibleOutcome / allowedDelayReason`。
- 已完成 本章焦点容量限制：活跃线程上下文已限制主推进 1 条、辅助推进 1-2 条，并把到期/超期伏笔焦点压到总量 3-5 条内。
- 已完成 超期伏笔硬约束升级：超期项会在上下文中以“本章必处理 / 必须写明延期”语言提升，不再只给软提醒。
- 已完成 质量面板接入：已增加支线真实兑现率、提及未推进计数、伏笔延期说明计数、超期失管计数。

## 三、当前已完成

- `story_threads` 和 `foreshadow_ledger` 已有支线与伏笔账本。
- `chapter_contracts` 能绑定服务线程和必需伏笔。
- `context.service.ts` 会注入活跃支线、应回收伏笔、开放事项。
- 章节门会检查必要线程是否被触及。

## 四、当前缺口

- “提及”和“推进”没有清晰区分。
- `payoffCondition` 容易是抽象短语，不能直接转成场景动作。
- 支线超期后多为警告，不一定强制进入下一章合同。
- 每章活跃线数量缺少硬上限，百万字后期容易信息过载。

## 五、详细设计

### 4.1 支线推进语义

新增或逻辑定义以下状态：

| 状态 | 含义 |
|---|---|
| mentioned | 只是提到，不改变信息或局势 |
| advanced | 有新行动、新信息、新后果 |
| blocked | 明确说明延期原因或阻碍 |
| paid_off | 完成回收或阶段解决 |
| stale | 超期未推进 |

章节门不能把 `mentioned` 当作 `advanced`。

### 4.2 伏笔回收条件动作化

把抽象回收条件拆成可写进场景的字段：

- `payoffSceneAction`：正文里必须发生什么动作。
- `requiredEvidence`：读者能看到什么证据。
- `readerVisibleOutcome`：本章结束后读者知道了什么。
- `allowedDelayReason`：如果不回收，允许怎样延期。

### 4.3 每章推进容量

建议硬限制：

- 主推进：1 条。
- 辅推进：1-2 条。
- 伏笔/支线合计最多 3-5 条进入正文焦点。
- 超出的线只进入背景，不进入本章任务。

### 4.4 合同接入

章节合同应明确：

- 本章必须推进的线。
- 本章可以轻触的线。
- 本章禁止展开的线。
- 本章必须回收或说明延期的伏笔。

## 六、实施步骤

1. 在支线和伏笔服务层定义推进语义。
2. 合同生成时区分 `mustAdvance`、`mayMention`、`mustPayoff`。
3. 合同验证器从正文抽取证据并判断推进状态。
4. 对超期线自动生成下一章候选硬约束。
5. 质量面板展示支线推进兑现率和超期线。

## 七、验收标准

- 支线推进率不再把“提到名字”算推进。
- 超期伏笔必须进入某章合同或标注延期原因。
- 每章活跃线数量可控。
- 用户能看到某条线最近在哪章真正推进过。

## 八、风险与建议

- 不要每章强行推进太多线，会稀释主线。
- 伏笔回收需要允许延期，但延期必须有原因和新目标章。
- 支线推进证据最好保留正文摘录，便于人工判断误判。
