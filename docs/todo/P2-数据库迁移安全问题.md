# P2 - 数据库迁移ALTER TABLE安全问题

> 优先级：P2（中等）
> 影响范围：升级时字段缺失或迁移报错
> 实现难度：低
> 类别：后端-数据库

---

## 问题

数据库迁移使用 `ensureColumn` 系列方法添加新字段。`ensureColumn` 本身已经先检查列是否存在，但原先迁移流程缺少步骤记录、事务边界和独立幂等测试；一旦升级中途失败，重复启动虽然通常不会直接撞到 `column already exists`，但仍可能留下“前半段已执行、后半段未执行”的不透明状态。

## 原因

- `db.ts` 中迁移逻辑长期依赖一次性顺序执行，缺少显式步骤记录
- 旧流程没有迁移版本号追踪，只能靠表级 `IF NOT EXISTS` 和列级 `ensureColumn` 被动兜底
- 缺少“每个迁移步骤一个事务”的边界，中途失败时难以确认执行到了哪一步
- 没有独立迁移测试验证重复执行与部分升级场景

## 解决方式

1. **保留并明确 `ensureColumn` 的列存在检查**：继续通过 `PRAGMA table_info()` 先判断后追加列
2. **迁移版本追踪**：新增 `_schema_migrations` 表记录 `0001_core_schema` 到 `0005_validate_schema` 的执行结果
3. **事务包裹迁移步骤**：每个迁移步骤都包裹在 SQLite transaction 内，失败时整步回滚
4. **迁移测试**：新增 `scripts/migration-safety.test.cjs`，覆盖空库初始化、重复执行和部分已存在字段的恢复场景

## 是否解决

已解决

## 预期效果

- 版本升级迁移100%安全，可重复执行
- 中途失败不会导致数据库处于不一致状态
- 用户无需手动干预数据库
