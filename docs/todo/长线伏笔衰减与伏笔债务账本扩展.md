# 长线伏笔衰减与伏笔债务账本扩展

关联总文档：[百万字小说生成问题分析与扩展方案](./百万字小说生成问题分析.md)

## 1. 问题定义

当前系统已经能在单章审校里识别部分“漏回收伏笔”问题，但对于百万字长线伏笔，仍缺少显式的登记、提醒、逾期和兑现管理机制。

## 2. 当前代码现状

- `electron/services/chapter.service.ts` 的审校结果里已有 `missing_payoffs`。
- `electron/services/story-prompts.ts` 会要求关注 `[即将回收]` 或 `[已N章未提及]` 的线索。
- `electron/services/story-memory.service.ts` 的 `mega` 模式存在线程衰减逻辑。
- 当前没有独立 `foreshadowLedger` 或兑现时间表。

## 3. 目前已解决 / 部分解决 / 未解决

- 已解决：已经意识到伏笔和回收问题，并有单章审校项。
- 部分解决：活跃线程和 prompt 规则能做弱提醒。
- 未解决：长线伏笔缺少账本化治理。

当前判断：`部分解决`

## 4. 潜在风险

- 长伏笔在几十章后被系统当作噪声淡化。
- 伏笔可能出现了，但没有目标回收章和逾期机制。
- 用户感受到“埋很多，收很少”或“收得太突兀”。

## 5. 原因分析

- 伏笔目前更多以文本描述形式存在，不是结构化对象。
- 活跃线程适合短中期跟踪，不适合长期债务管理。
- 当前没有“首次出现 -> 中间提醒 -> 到期回收 -> 实际回收”的完整链路。

## 6. 扩展方案

- 新增 `foreshadowLedger`，把伏笔从说明文字变成结构化记录。
- 每条伏笔至少记录首次出现章、关联人物、目标回收章、当前状态、实际回收章。
- 区分“短期线程”和“长期伏笔债务”，避免被普通 thread decay 误伤。
- 卷级和全书级面板显示“逾期伏笔”“临近回收伏笔”“已完成回收伏笔”。

## 7. 建议的数据结构 / 指标 / 页面能力

- `foreshadowLedger`
- `foreshadowStatus`: active / due / overdue / paid_off
- `payoffSpan`: 从埋伏笔到回收跨了多少章
- `overdueForeshadowCount`
- 写作页或质检页新增“本章应回收伏笔”区块

## 8. 实施优先级

等级：`S级`

等级说明：铺垫与回收是长篇核心结构能力，缺失会直接破坏全书完成度。

原因：伏笔系统直接决定长篇读感和全书结构完成度。

## 9. 验收标准

- 每条关键伏笔都可在系统中追踪生命周期。
- 卷级和全书级可统计逾期未收伏笔。
- 本章生成前可提示即将到期或必须回收的伏笔。
- 审校阶段能识别“应该回收但未回收”的问题，不再只依赖自然语言推断。
