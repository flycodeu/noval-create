# 资产变更影响分析与写作闭环自动化

## 一、目标

把现有“资产 -> 章节 -> 回写 -> 修订”的页面串联，升级成自动闭环引擎。系统需要明确知道：

- 哪个资产变了
- 会影响哪些章节、线程、时间轴和合同
- 写作时要注入哪些最新上下文
- 本章新增了哪些事实和状态变化
- 哪些冲突需要进入修订中心

## 二、为什么现在要做

长篇系统真正的护城河不在单次生成，而在持续一致性。如果资产修改后仍靠用户自己去找受影响章节，闭环价值就会被大幅削弱。

## 三、当前已覆盖基础

- `context-impact.service.ts` 已负责上下文变更感知、章节发布检查和部分 stale 标记。
- `09-章后状态回写中心` 已能写回角色状态、世界状态、时间线锚点和部分故事记忆。
- `18-章节场景合同执行器`、`20-审校反哺与复现率闭环`、`26-章节验收门与自动重写` 已形成合同校验、问题回流和自动修复基础。
- `修订中心` 已能接收写回失败、章节门失败和待人工确认任务。

## 四、待办拆分

- [x] 已有上下文变更标记、章节发布检查、修订任务和章后回写基础能力。
- [x] 将资产变更事件标准化，统一承载变更对象、变更原因、影响级别和时间戳。
- [x] 新增影响范围识别器，覆盖章节、卷级目标、线程、时间轴、伏笔和人物状态。
- [x] 将影响结果自动生成待同步任务，而不是只提示上下文已变更。

- [x] 冲突或低置信度事实自动触发一致性校验、修订任务或人工确认。
- [x] 为作者提供影响面板，显示“这次改动影响了什么、用了什么、忽略了什么”。

## 五、详细设计

### 5.1 标准闭环

目标链路固定为：

资产变更 -> 影响分析 -> 待同步任务 -> 写作注入 -> 章后事实抽取 -> 总账回写 -> 一致性校验 -> 修订中心

### 5.2 影响对象

至少覆盖以下对象：

- 章节合同 / 场景合同
- 已写章节与待写章节
- 故事线程、伏笔与信息差
- 时间轴事件
- 角色状态 / 世界状态
- 卷级目标与终局承诺

### 5.3 可解释性

每次生成都要说明：

- 用了哪些资产
- 用了哪些合同条款
- 忽略了哪些约束
- 新增了哪些事实
- 哪些事实为低置信度，待人工确认

## 六、验收标准

- 任一关键资产修改后，系统能自动定位受影响对象，而不是只提示“可能过期”。
- 写作时可见本次注入的关键资产、合同和状态来源。
- 章后回写能够区分高置信度事实与待确认事实。
- 冲突能够自动进入修订中心，并可追溯到来源变更。

## 七、风险与建议

- 影响分析不能只做关键词匹配，否则误报和漏报都会过高。
- 自动回写必须有置信度分层，不能把模型推断当硬事实。
- 修订中心要承接“自动同步失败”与“需要人工确认”两类不同任务。
