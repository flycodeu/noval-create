# 长篇写作技术架构

## 一、目标

在保留现有上下文与章节流水线基础上，把系统升级成更稳定的多角色协作架构，用更少的漂移支撑更长的正文。

## 二、当前已完成

- [x] `context.service.ts` 已形成多层上下文：故事核心、当前弧线、人物状态、世界状态、线程压力、时间轴、长期记忆、硬约束、软上下文预算。
- [x] `chapter.service.ts` 已拆分写作阶段：`planning / drafting / reviewing / rewriting`。
- [x] `story-memory.service.ts` 已有长期记忆与 checkpoint 机制。
- [x] 任务系统已支持异步任务、工作流任务和规划草稿。
- [x] `章后状态回写中心` 已落地，Canonizer 可以把章节产出转成事实抽取、状态 diff、人工确认和统一写回的可视化闭环。

## 三、当前已补齐

- [x] `chapter.service.ts` 已把章节正文升级为 `chapter_write` 总控工作流，并显式落地 `Planner / Writer / Critic / Rewriter / Canonizer / Finalize` 子任务。
- [x] `Writer / Critic / Rewriter` 已强制绑定 `contractVersion` 与章节/场景合同摘要，缺失时会直接阻断并给出恢复入口。
- [x] `Canonizer` 已并入正文流水线主链，直接复用 `WritebackCenter` 与 `chapter_writeback_runs` 作为章后状态差异草案。
- [x] 写作失败、Canon 草案失败与页面恢复入口已通过 `recoveryHintJson`、任务中心与写作页全链路打通。
- [x] 任务中心、正文写作页、创作总览与质量监控均已展示角色阶段、耗时 / tokens 与常见恢复点。

## 四、模块价值

- 单一模型“一把梭”越长越不稳。
- 现有分层上下文已经够强，下一步关键是职责分离，而不是继续把所有摘要塞给同一个生成步骤。

## 五、当前能力结构

- 当前主链路包含六个角色阶段：
  - `Planner`：生成卷级、章节、场景合同
  - `Writer`：只按合同写正文
  - `Critic`：检查连续性、节奏、角色口吻、AI 味
  - `Rewriter`：只处理失败场景或失败段落
  - `Canonizer`：从正文抽取事实并准备回写
  - `Finalize`：负责章节状态收口、结果整合与恢复提示
- 当前六层记忆使用原则：
  - `硬设定层`
  - `风格层`
  - `状态层`
  - `弧线层`
  - `章节合同层`
  - `场景局部层`

## 六、页面与交互

- 在任务中心中显示每个章节流水线由哪个角色阶段负责。
- 在正文写作页显示“合同生成、正文生成、审校、重写、Canon 回写”全链路状态。
- 在质量监控中展示不同角色阶段的失败分布与常见回退点。

## 七、数据结构 / 状态字段

- 现有 `tasks` 可继续复用，新增：
  - `pipelineRole`
  - `pipelineStage`
  - `upstreamTaskId`
  - `contractVersion`
  - `canonRunId`
  - `recoveryHintJson`
- 现有上下文结构继续保留，不推翻。

## 八、与现有模块的关系

- `context.service` 继续负责上下文分层与预算控制。
- `章节合同与场景合同` 成为 Planner 的主要产物。
- `章后状态回写中心` 成为 Canonizer 的交互面。
- `章节验收门` 成为 Critic 结果进入状态流转的出口。

## 九、验收标准

- 章节流水线的每一步都有清晰角色归属。
- Writer 不再直接消费泛化大纲，而是消费合同。
- Canonizer 结果可被人工确认并回写。
- 失败链路可明确区分“重写正文”“重跑合同”“重做回写”。
