# 上下文与记忆调度

## 一、目标

让百万字生成时上下文既足够完整，又不会因为堆叠过多材料导致硬约束被挤掉。系统必须明确区分“必须保留的事实”和“可裁剪的背景”。

## 二、当前已完成

- `context.service.ts` 已构造故事核心、章节目标、人物状态、世界状态、关系、物品、时间轴、活跃线程、长期记忆和向量召回。
- `allocateChapterContext` 已区分硬约束和软上下文。
- 硬约束包括章节目标、人物当前状态、世界状态、关键人物关系、关键物品去向、必须回收事项、必须承接。
- 硬约束丢失或截断会触发 `HardConstraintOverflowError`。
- 长篇目标字数达到 35 万/80 万时，硬约束预算已有上浮逻辑。
- `story_memory_checkpoints` 已能保存长文压缩记忆和禁用方向。

## 三、当前缺口

- 上一章正文仍主要使用末尾 300 字，对 3000-5000 字章节覆盖不足。
- 先验文本没有按场景切点、关键对话、决策点、伏笔点采样。
- 软上下文被裁剪后，用户不知道具体裁掉了什么。
- 近章摘要、长期记忆和向量召回之间还缺少明确优先级说明。
- 百万字后期需要更多 checkpoint 策略，避免只靠最近章节摘要。

## 四、详细设计

### 4.1 上下文层级

| 层级 | 内容 | 裁剪策略 |
|---|---|---|
| L1 硬约束 | 章节目标、人物状态、世界状态、必须承接、必须回收 | 不得丢失 |
| L2 直接先验 | 上一章关键正文采样、上一章 seed | 优先保留 |
| L3 近章连续性 | 最近 3-5 章摘要、连续性状态 | 可压缩 |
| L4 长期记忆 | checkpoint、卷级摘要、长期状态 | 可摘要 |
| L5 背景补充 | 向量召回、风格参考、软世界观 | 可裁剪 |

### 4.2 PreviousChapterSampler

新增 `PreviousChapterSampler`，替代简单末尾截断。

输入：

- 上一章正文。
- 上一章场景计划。
- 上一章连续性状态。
- 上一章审校意见。
- 章后状态 diff。

输出：

- 1000-1800 字上一章先验。
- 包含以下片段：
  - 最后 300 字。
  - 关键决策段。
  - 未回收伏笔段。
  - 人物状态变化段。
  - 强冲突或反转段。
  - 下一章 seed。

采样原则：

- 不是简单摘要，要保留可承接的原文细节。
- 不采无关铺陈和重复心理活动。
- 如果上一章内容不足 1000 字，则全量注入。

### 4.3 ContextLossReport

上下文构造后生成裁剪报告：

- 本章硬约束注入清单。
- 软上下文保留清单。
- 被裁剪字段。
- 裁剪原因：预算不足、优先级低、已被硬约束覆盖。
- 用户需要人工确认的风险。

### 4.4 长篇 checkpoint 策略

建议默认：

- 每 10 章生成一个 checkpoint。
- 每卷结束生成卷级 checkpoint。
- 重大状态变化后可手动锁定 checkpoint。
- stale checkpoint 不参与硬事实，只作为背景参考。

## 五、实施步骤

1. 在 `context.service.ts` 中抽出上一章采样函数。
2. 将 `lastChapterEnding` 从末尾 300 字升级为 `previousChapterContext`。
3. 在上下文预览中展示采样来源和裁剪报告。
4. 将 checkpoint 间隔接入百万字生产设置。
5. 质量面板增加“上一章有效馈送覆盖率”。

## 六、验收标准

- 上一章有效馈送覆盖率达到 30% 以上，或至少 1000 字。
- 任何一章生成前能展示硬约束注入清单。
- 裁剪发生时，用户知道裁掉了哪些软上下文。
- 硬约束不得因为 token 预算不足被静默丢弃。
- 10 章以上的承接主要依赖 checkpoint 和结构化状态，而不是长 prompt 堆叠。

## 七、风险与建议

- 上一章采样不能无限扩容，否则会挤压本章合同和人物状态。
- 原文片段比摘要更利于承接，但也更耗 token，需要严格控制在 1000-1800 字。
- checkpoint 要标记 stale 状态，避免旧摘要覆盖新事实。
