# 上下文与记忆调度

## 一、目标

让百万字生成时，上下文基础层既足够完整，又不会因为堆叠过多材料导致硬约束被挤掉。系统必须明确区分“必须保留的事实”和“可裁剪的背景”。

本模块的定位固定为“基础上下文调度层”，而不是最终版统一 AI 上下文组装器。

## 二、模块定位与边界

`16-上下文与记忆调度` 当前只负责基础层能力：

- 章节生成前的基础上下文装配。
- 硬约束优先注入与预算保护。
- 上一章关键先验采样与展示。
- 近章摘要、长期记忆和向量召回结果接入。
- 上下文裁剪报告、采样报告与预览面板。

本模块当前不包含以下增强层能力：

- 图谱召回、时间召回、合同召回的统一编排。
- “为什么选这些上下文”的结构化选择报告。
- 结构化上下文对象优先于自然语言的统一组装器。
- 模型路由、多轮审校链、作者风格锁、生成可解释性。

上述增强能力统一归入 `34-AI引擎强化与可解释生成`，不继续并回本模块状态。

## 三、本轮已落地

- `context.service.ts` 新增 `buildPreviousChapterContextFeed`，将上一章输入从“末尾 300 字”升级为结构化先验采样。
- 新增 `previousChapterContext`、`previousChapterSampleReport`、`softContextDecisions` 三类数据，覆盖生成链路、预览面板和质量面板。
- `allocateChapterContext` 现在会返回逐字段软预算决策，明确区分“保留 / 截断 / 丢弃 / 走硬约束通道”。
- `chapter.service.ts` 已把 `previousChapterContext` 接入 `scenePlan / draft / review / rewrite` 四阶段 prompt。
- 正文写作页已增加“上一章关键先验”卡片，并在“关键约束注入”卡片展示软预算裁剪明细。
- 质量看板已增加“上一章先验覆盖率 / 平均采样字数”汇总与卷级指标。

## 四、实现结果

### 3.1 上下文层级

| 层级 | 内容 | 裁剪策略 |
|---|---|---|
| L1 硬约束 | 章节目标、人物状态、世界状态、必须承接、必须回收 | 不得丢失 |
| L2 直接先验 | 上一章关键正文采样、上一章 seed | 优先保留，优先级高于近章摘要 / 长期记忆 / 向量召回 |
| L3 近章连续性 | 最近 3-5 章摘要、连续性状态 | 可压缩 |
| L4 长期记忆 | checkpoint、卷级摘要、长期状态 | 可摘要 |
| L5 背景补充 | 向量召回、风格参考、软世界观 | 可裁剪 |

### 3.2 PreviousChapterSampler

已实现 `buildPreviousChapterContextFeed`，替代简单末尾截断。

输入：

- 上一章正文。
- 上一章场景计划。
- 上一章连续性状态。
- 上一章审校意见。
- 章后状态回写摘要与 diff reason。

输出：

- 常规情况下输出 1000-1800 字左右的“上一章关键先验”。
- 片段来源已覆盖：
  - 上一章开场 / 中段 / 末尾原文片段。
  - 上一章摘要。
  - 连续性状态变化。
  - 场景计划锚点。
  - 审校重点。
  - Canon / 状态回写摘要。
  - 下一章 seed。

采样原则：

- 不是简单摘要，要保留可承接的原文细节。
- 不采无关铺陈和重复心理活动。
- 如果上一章正文不足 1000 字，则按全文注入并额外拼接 seed。

### 3.3 ContextLossReport

上下文构造后现在会生成裁剪报告：

- 本章硬约束注入清单。
- 软上下文逐字段决策。
- 被裁剪字段。
- 裁剪原因：预算不足、已被硬约束覆盖。
- 上一章采样来源、覆盖率和段落清单。

### 3.4 长篇 checkpoint 策略

现状：

- 每 10 章生成一个 checkpoint。
- 每卷结束生成卷级 checkpoint。
- 重大状态变化后可手动锁定 checkpoint。
- stale checkpoint 不参与硬事实，只作为背景参考。

## 五、验收结果

- 上一章有效馈送覆盖率达到 30% 以上，或至少 1000 字。
- 任何一章生成前都可展示硬约束注入清单。
- 裁剪发生时，用户可见被裁掉或压缩的软上下文字段。
- 硬约束仍然保持预算阻断，不会静默丢弃。
- 上下文预览与质量看板都已能显示上一章先验覆盖率。

## 六、剩余建议

- 上一章采样不能无限扩容，否则会挤压本章合同和人物状态。
- 原文片段比摘要更利于承接，但也更耗 token，后续仍应继续观察 80 万字以上项目的裁剪频率。
- checkpoint 要标记 stale 状态，避免旧摘要覆盖新事实。

## 七、与 34 的职责边界

当前文档解决的是“上下文与记忆调度”的基础层，重点在硬约束优先、上一章关键先验、向量召回结果接入和软预算裁剪；它不等于最终版的 AI 上下文组装器。

职责拆分固定如下：

- `16` 负责基础装配、预算控制、采样报告、预览与当前向量召回接入。
- `34` 负责统一上下文组装器、三层召回合成、结构化选择报告、模型路由、多轮审校链与生成可解释性。

后续增强统一并入 `34-AI引擎强化与可解释生成`，`16` 不再通过叠加新概念改变完成状态。

## 八、代码入口映射

当前实现的主要代码入口：

- `electron/services/context.service.ts`
  负责基础上下文装配、上一章关键先验采样、召回结果接入和预算分配。
- `electron/services/chapter.service.ts`
  负责把基础上下文注入 `scenePlan / draft / review / rewrite`，并组装上下文预览。
- `src/types/index.ts`
  负责 `ChapterContextPreview`、`RecallSnapshot`、`ContextDecisionEntry` 等共享类型。
