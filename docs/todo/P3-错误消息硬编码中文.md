# P3 - 错误消息硬编码中文

> 优先级：P3（改进）
> 影响范围：国际化能力
> 实现难度：高
> 类别：全局-工程规范 / 用户可见消息治理

---

## 问题

前后端大量用户可见错误消息、状态提示、fallback 文案直接硬编码在业务逻辑里，分散在 `electron/services`、`electron/utils`、`src/pages` 等多个层级。  
这会带来两个问题：

- 统一修改提示文案成本高，容易同义不同词
- 如果后续要支持 i18n，需要逐个文件回收字符串，迁移成本高

## 原因

- 项目初期面向中文用户开发，未引入 i18n 框架
- 用户可见消息直接写在业务逻辑中，无统一消息源
- IPC 校验层、服务层和页面 fallback 各自维护一套字符串，缺少共享约束

## 解决方式

1. 建立共享消息目录，至少把用户可见消息从业务代码中抽离
2. 在 `electron` 侧引入轻量 `UserFacingError`，避免继续直接 `throw new Error('中文文案')`
3. 在前端引入统一消息 helper，页面 fallback 不再裸写中文
4. 远期如需国际化，可在现有 message key 基础上接入 i18n 框架，而不是重新回收字符串

## 合法例外

- 本次建立的是“统一消息源 + key”，不是完整 i18n 运行时；当前文案仍然默认中文
- Prompt、AI 生成模板、内部日志文本不在本轮治理范围内
- 少量需要保留上下文细节的自由文本诊断仍允许存在：
  - 例如 `map.service.ts` / `premise.service.ts` 中带原始输出片段、修复摘要或动态批次上下文的错误
  - 这类文本不是固定 fallback，而是运行时诊断，不强制压平到单个 message key
