# P3 - 生成管线4次上下文构建造成重复数据库查询

> 优先级：P3（改进项）
> 影响范围：生成效率
> 实现难度：中

---

## 问题

`generateChapterContent()` 在生成管线启动时，对同一章节调用了 4 次 `buildChapterContext()`（分别用于 scenePlan、draft、review、rewrite 四个阶段）：

```typescript
const scenePlanContext = await stageContext('scenePlan')
const draftContext = await stageContext('draft')
const reviewContext = complexity === 'simple' ? draftContext : await stageContext('review')
const rewriteContext = await stageContext('rewrite')
```

每次 `buildChapterContext()` 都会重新查询同一组数据（小说、章节列表、角色、关系、故事弧、道具、时间线、世界地图、故事线索等），区别仅在于 token 预算分配策略不同。

以 standard 复杂度为例，一章生成会执行 4 次完整的上下文构建，每次约 10-15 次数据库查询，总计 40-60 次查询中有约 30-45 次是重复读取相同数据。

## 原因

`buildChapterContext()` 设计为无状态函数，不缓存中间数据。每个 stage 需要不同的 token 预算分配，但底层数据完全相同。

## 解决方式

将 `buildChapterContext` 拆分为两步：
1. `collectChapterContextRawData(novelId, chapterNum)` — 只读一次数据库，返回原始数据与已整理的上下文片段
2. `allocateChapterContext(rawData, options)` — 根据 stage/complexity 做 token 分配

`generateChapterContent()` 改为先收集一次 raw data，再为 `scenePlan / draft / review / rewrite` 4 个阶段复用同一份数据，只在分配阶段有不同行为。

## 是否解决

已解决

## 预期效果

- 每章生成的数据库查询从 40-60 次降至 10-15 次
- 批量生成 100 章节约 3000-4500 次数据库查询
