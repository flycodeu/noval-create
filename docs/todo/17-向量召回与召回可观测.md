# 向量召回与召回可观测

## 一、目标

让向量召回从“隐性辅助能力”变成“可追踪质量信号”。百万字生成中，召回服务异常或命中旧片段都会导致连续性退化，必须能被记录、展示和阻断批次。

## 二、当前已完成

- `chapter_embeddings` 已存章节片段，支持摘要、连续性、seed 等 fragment。
- `context.service.ts` 已使用多信号召回，查询角色、世界规则、支线、伏笔、连续性等历史信息。
- 召回失败时会降级到结构化状态，并写入 `recallDiagnostics`。
- 章节门已有“召回补充未依赖过期片段”检查。
- `chapter.service.ts` 在 Finalize 后会异步生成章节向量。

## 三、当前缺口

- 每次生成的召回结果没有持久化，无法事后追溯。
- 召回失败不会成为批次暂停条件。
- 无法统计连续多少章使用了召回兜底。
- 无法按 bucket 分析召回命中质量，例如角色命中足够但伏笔命中为 0。
- 用户只能看到部分诊断，不能看到“本章是否真用了召回”。

## 四、详细设计

### 4.1 召回快照

新增或复用任务输出记录以下字段：

```ts
retrieval_snapshots {
  id
  novelId
  chapterId
  taskId
  retrievalUsed
  hitCount
  bucketStatsJson
  staleRecallCount
  fallbackReason
  createdAt
}
```

`bucketStatsJson` 示例：

```json
{
  "character": { "hitCount": 3, "staleCount": 0 },
  "world": { "hitCount": 2, "staleCount": 1 },
  "thread": { "hitCount": 0, "staleCount": 0 },
  "foreshadow": { "hitCount": 1, "staleCount": 0 }
}
```

### 4.2 降级原因

标准化 `fallbackReason`：

- `embedding_service_failed`
- `query_embedding_failed`
- `no_hits`
- `only_stale_hits`
- `budget_trimmed`
- `disabled_by_config`

### 4.3 质量面板指标

新增召回健康指标：

- 召回可用率。
- 平均命中数。
- bucket 覆盖率。
- 过期片段率。
- 连续降级章节数。
- 最近一次降级原因。

### 4.4 批次暂停条件

建议规则：

- 连续 3 章召回失败：暂停批量生成。
- 单章 stale recall 超过 3 条：生成修复任务。
- 当前批次召回可用率低于 80%：批次结束后强制复盘。
- 召回失败但硬约束完整：允许单章继续，但标记风险。

## 五、实施步骤

1. 在 `context.service.ts` 的召回执行后形成 snapshot 对象。
2. 将 snapshot 写入新表或 `tasks.outputText/inputJson` 的结构化字段。
3. 在 `quality-dashboard.service.ts` 聚合召回健康趋势。
4. 在章节门中把连续降级作为 warning/blocker。
5. 在批次总控中接入暂停条件。

## 六、验收标准

- 每次生成都能看到 `retrievalUsed / hitCount / fallbackReason`。
- 召回失败不再是静默质量下滑。
- 质量面板能按卷/批次展示召回降级趋势。
- 用户能一键定位召回过期片段对应章节。
- 连续召回失败能阻止继续批量生成。

## 七、风险与建议

- 召回只能作为背景补充，不能覆盖硬约束和结构化状态。
- 不要把命中数高等同于质量高，必须同时监控 stale 率。
- 如果嵌入服务成本高，可先只持久化诊断，不立即扩大召回数量。
