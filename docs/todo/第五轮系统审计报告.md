# 第五轮系统审计报告（百万字 AI 小说工程化剩余缺口）

> 审计日期：2026-04-05
> 审计目标：检查当前系统在百万字场景下是否仍存在流程缺步骤、上下文弱关联、AI 味残留、背景/主题漂移、批量生成不可恢复，以及上下文压缩不适合长任务拆分的问题

---

## 一、结论总览

当前系统已经不再处于“完全无法支撑长篇”的阶段。正文主链路已经具备相对完整的 `场景计划 → 初稿 → 审校 → 重写` 闭环，章节级的人类语言修正、上下文漂移审查、弧推进审查也已经明显增强。

但从“单章可写”走向“百万字可持续生产”，还剩下 5 个结构性缺口，其中 **P0 1 个、P1 4 个**：

| 优先级 | 文件 | 核心问题 | 当前状态 |
|--------|------|----------|----------|
| P0 | [P0-批量生成仅拆批未持久化断点.md](P0-批量生成仅拆批未持久化断点.md) | 角色/物品/时间轴/线程等批量任务可拆批但大多不可续跑 | 已解决 |
| P1 | [P1-工作流门禁只校验存在不校验新鲜度与质量.md](P1-工作流门禁只校验存在不校验新鲜度与质量.md) | 工作流入口只看“有没有”，不看“是不是最新、够不够好” | 未解决 |
| P1 | [P1-上下文压缩仍是自由文本拼接而非最小实体卡.md](P1-上下文压缩仍是自由文本拼接而非最小实体卡.md) | 长文本上下文仍偏自由文本块，不利于批量拆分与稳定回灌 | 未解决 |
| P1 | [P1-向量召回查询过窄导致关键上下文漏召回.md](P1-向量召回查询过窄导致关键上下文漏召回.md) | 召回 query 只看大纲/弧目标，容易漏掉关系、主题、规则冲突 | 未解决 |
| P1 | [P1-非正文生成链缺少审校重写闭环.md](P1-非正文生成链缺少审校重写闭环.md) | 正文治理较强，但人物/物品/线程/时间轴等上游资产缺少同级闭环 | 未解决 |

一句话结论：**现在的主要风险已经不是“单章写不出来”，而是“上游资产与批量流程还没有完全工程化”，这会在 300-400 章、几十个批量任务和长期迭代中放大成系统性漂移。**

## 二、六个维度审计结论

### 1. 流程门禁

目前工作流入口已经有 blocker 机制，但 `src/pages/Novel/workflow.ts` 中的 `getWorkflowBlockers()` 仍然主要基于字段存在性和数量判断，例如是否有 `worldRulesJson`、`outlineCount > 0`、`timelineCount > 0`、`threadCount > 0`。

这意味着系统能阻止“完全没准备”的情况，但还不能阻止以下高风险情况：

- 世界规则已经改过，但人物/物品/线程还是旧版本
- 立项、主题、主角设定已经改过，但时间轴与大纲没有重新同步
- 记忆检查点或长文摘要已经过期，但正文入口仍然放行
- 上游资产虽然存在，但语言质量、背景一致性、主题对齐并没有达标

结论：**门禁已存在，但仍属于“存在性门禁”，还不是“质量/新鲜度门禁”。**

### 2. 上下文压缩

`electron/services/context.service.ts` 的 `buildCharacterStates()` 仍把角色状态拼成较长的自然语言行；`electron/services/story-memory.service.ts` 的 `buildStoryMemoryPromptSummary()` 也以多段文本摘要为主。

这套机制比早期纯回溯章节已经强很多，但离“适合百万字拆批生成的最小实体卡”还有明显距离。当前上下文仍存在两个问题：

- 表达过长，容易挤占 token 预算
- 结构不稳定，不同批次之间难以稳定回灌同一套核心约束

结论：**上下文已经有分层摘要，但还没有彻底切换到“固定世界底座 + 最小实体卡 + 动态召回记忆”的稳定结构。**

### 3. 批量生成与恢复

人物、物品、时间轴、故事线程、支线等链路基本都已经具备拆批意识，但大多数实现仍是服务内 `for/while` 循环调用 `runChatTask()`。一旦任务中途失败、窗口关闭或需要第二天继续，通常无法从“第 N 批”继续，只能重新发起或依赖局部已有结果。

对照之下，地图与世界规则已经接入 `workflow` 型任务，并支持 `resumeWorkflowTask()`。

结论：**系统已经从“一次性全量生成”升级到“可拆批生成”，但还没有全面升级到“可持久化续跑的批处理工作流”。**

### 4. 语言质量与 AI 味

正文链路已经显著进化：`chapter.service.ts` 中存在审校结果结构、语言风险、上下文漂移风险、人类语言修复建议和重写阶段。

但这套能力没有完整下沉到人物、物品、时间轴、线程等上游资产生成。上游资产如果带着模板腔、设定味、空洞摘要进入系统，后续章节即使有审校，也是在“脏输入”之上补救。

结论：**正文主链路的人类语言治理已经成型，但非正文资产层仍缺少同级别闭环。**

### 5. 背景、主题与关系对齐

当前不少 prompt 已经会带上 `storyCore`、`relationSummary`、`worldRulesSummary` 等信息，但 `context.service.ts` 中的向量召回 query 目前仍主要由“当前章节大纲 + 当前故事弧目标”组成。

这会让以下内容更容易漏召回：

- 长时间未出场但和当前章节强相关的角色关系
- 某个地点、物品、势力的旧约束
- 主题回收点、母题呼应、长期冲突线
- 世界规则中的禁忌或代价条款

结论：**背景和主题约束已被部分写进 prompt，但召回层还没有把这些约束真正变成稳定的检索信号。**

### 6. 剩余工程风险

当前最容易放大为系统性问题的，不是某个 prompt 细节，而是“脏资产传播”与“中断后重跑成本”：

- 上游资产质量不稳定，会把偏题、AI 味、关系失真持续传到后续章节
- 批量任务不可续跑，会让几十个生成请求在真实使用中变得脆弱
- 上下文缺少最小卡片化表达，会让拆批后很难精确保留核心约束

结论：**第五轮的重点已经从“单点质量优化”转为“全链路工程闭环补完”。**

## 四、建议修复顺序

1. 先补 **P0 批量任务续跑能力**。这是几十个生成请求场景下最容易真实踩中的工程故障点。
2. 再补 **工作流质量门禁 + 最小实体卡上下文**。这是让拆批任务真正可控的基础。
3. 然后补 **多信号召回 + 非正文资产审校重写**。这是把“背景/主题/关系”从 prompt 口号变成系统闭环的关键。

不建议继续只加 prompt 规则而不补流程与状态机。因为第五轮暴露的主要矛盾已经不是“提示词不够狠”，而是“状态、上下文、批处理没有完全工程化”。

## 五、审计依据（核心代码位置）

- `src/pages/Novel/workflow.ts`
  - `getWorkflowBlockers()` 主要按存在性和数量放行
- `electron/services/context.service.ts`
  - `buildCharacterStates()` 仍以自然语言长行拼接角色状态
  - `findSimilarFragments()` 的 query 目前主要来自 `outline + arcGoal`
- `electron/services/story-memory.service.ts`
  - `buildStoryMemoryPromptSummary()` 仍以多段文本摘要拼接长记忆
- `electron/services/chapter.service.ts`
  - 已具备 `review` / `rewrite` / `human_language_repairs` / `context_drift_risks` 闭环
- `electron/services/character.service.ts`
- `electron/services/item.service.ts`
- `electron/services/timeline.service.ts`
- `electron/services/story-thread.service.ts`
- `electron/services/core-settings.service.ts`
  - 上述链路已具备拆批生成，但大多仍是服务内循环，不是统一的可恢复工作流
- `electron/services/workflow-task.service.ts`
  - 当前可恢复 workflow 主要覆盖地图、世界规则
- `electron/services/map.service.ts`
  - 已体现父任务/子任务和可恢复工作流的形态，可作为其他批量链路的参考基线
