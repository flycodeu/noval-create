# 事件锚点状态系统

## 一、目标

解决百万字生成中的状态跳变问题。角色伤势、目标、立场、心理、关系温度和世界状态变化，都必须能追溯到具体事件和场景，而不是只有“第 N 章变成 X”。

## 二、当前已完成

- `character_state_versions` 已有伤势、资源、立场、心理、关系温度、目标、`eventCause`、`changeReason`。
- `world_state_versions` 已有 `eventCause`、`changeReason`、`sourceKind`、`sourceRef`。
- `character-state.service.ts` 会检测缺少明确事件原因的状态跳变。
- 上下文提示中会注入“第 N 章 + 状态摘要 + 变更原因”。
- Canonizer 已能生成章后状态差异草案。

## 三、当前缺口

- 缺少 `triggerEventId` 或 `sourceSceneId`。
- 缺少结构化 `stateDelta`：从 A 到 B、变化幅度、持续时间、是否可逆。
- 章节内多次变化容易被压缩成章末终态。
- Canonizer 抽取出的状态 diff 需要更细粒度连接到事件和场景。

## 四、详细设计

### 4.1 EventAnchor

新增事件锚点：

```ts
event_anchors {
  id
  novelId
  chapterId
  segmentId
  eventType
  eventSummary
  participantsJson
  causedStateDiffsJson
  createdAt
}
```

事件类型：

- `injury`
- `resource_change`
- `relationship_shift`
- `goal_change`
- `world_rule_change`
- `item_transfer`
- `reveal`
- `battle_result`

### 4.2 状态 delta

状态版本扩展逻辑：

```ts
StateDelta {
  field: string
  before: string
  after: string
  cause: string
  persistencePolicy: 'temporary' | 'ongoing' | 'resolved' | 'unknown'
}
```

Prompt 注入不再只写：

- “第 12 章：林远受伤。”

而写：

- “第 12 章因三号楼伏击，林远左臂撕裂伤，从可战斗变为行动受限；该伤势持续到后续章节，未确认恢复。”

### 4.3 章节内多次变化

如果同一角色在同章内多次变化，保留事件链：

- 交战前状态。
- 交战后受伤。
- 觉醒/决策后的目标变化。
- 章末仍未解决的问题。

这条链进入下一章先验，而不是只保留最终状态。

## 五、实施步骤

1. 在 Canonizer 输出中增加事件锚点草案。
2. 章后状态回写中心展示“事件 -> 状态变化”关系。
3. 状态版本增加或逻辑关联 `triggerEventId/sourceSegmentId/stateDeltaJson`。
4. `context.service.ts` 注入状态因果链。
5. 章节门检查状态跳变是否有事件锚点。

## 六、验收标准

- 下一章能准确承接上一章伤势、目标、关系温度和资源状态。
- 角色状态跳变能追溯到具体事件。
- 章节内多次转折不会只保留最后一个状态。
- 世界状态变化能说明来源和持续性。

## 七、风险与建议

- 事件锚点不应变成时间轴重复建设，重点是服务状态承接。
- 第一版可以只锚定人物和世界状态重大变化。
- 人工确认入口很重要，自动抽取状态因果会有误判。
